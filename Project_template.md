# Задание 1. Анализ и планирование


### 1. Описание функциональности монолитного приложения

**Пользовательские функции**

- Пользователи могут просмотреть показатели датчиков температуры;
- Пользователи могут установить желаемое значение температуры;
- (?) Пользователи могут запросить отключение их дома от системы;
- Температурные данные синхронно запрашиваются сервером непосредственно у датчиков
в момент их запроса пользователем.

**Административные функции:**

- Специалист по подключению к системе может добавить пользователя/термостат в неё;
- (?) Администратор системы может отключить пользователя от системы (не указано, но предполагается).


### 2. Анализ архитектуры монолитного приложения

- Язык программирования: Java
- База данных: PostgreSQL
- Архитектура: Монолитная, все компоненты системы (обработка запросов, бизнес-логика, работа с данными) находятся в рамках одного приложения.

### 3. Определение доменов и границы контекстов

В исходной системе определены следующие домены:

- Домен управления пользователями (административный)
- Домен управления устройствами
    - поддомен регистрации устройств (административный)
    - поддомен получения/установки температуры

>⚠️ В исходных данных ️ не указана as-is модель оплаты. 
> Возможно, сервис предоставляется бесплатно при установке комплекта оборудования,
> или же как разовая покупка. В противном случае здесь должен быть добавлен
> домен биллинга.

### **4. Проблемы монолитного решения**

Используемый на данный момент архитектурный подход к реализации приводит к следующим проблемам:

- Проблемы с масштабированием (доступно только вертикальное);
- Более высокий TTM для новых функций и, что важнее, для багфиксов;
- Необходимость унификации технологического стэка для всех членов команды (не проблема, но может стать);
- Высокая скорость отклика за счёт поллинга датчиков в момент запроса;
- Невозможность самостоятельного подключения к / отключения от системы;
- Отсутствие хэлпдеска для оперативного решения проблем у пользователей.
